Agent-oriented virtual Git workspace

Mount the commit. Don't clone the repository.

GFS is a Git-compatible repository service plus a Rust FUSE client, built for short-lived coding-agent jobs. A job mounts an immutable Git snapshot, sees an ordinary directory tree, and downloads file data only when a process actually opens a file. Writes land in a local copy-on-write overlay. Code discovery goes through a revision-aware server search API, so searching a monorepo hydrates nothing.

The problem · and the shape of the answer

A clone is the wrong unit of work for a job that touches twenty files

A hosted coding agent starts, reads a handful of files, greps for a symbol, edits four paths, and exits. Git's startup cost is sized for a human who will keep the checkout for months. Cloning microsoft/vscode costs 56.2 s and 1 648 MiB before the agent reads its first line; shallow plus blobless — the best existing combination — still costs 10.0 s and 363 MiB, because the working tree is checked out in full either way. On the Linux kernel the same two numbers are 383 s / 8 087 MiB and 19.5 s / 1 839 MiB.

Partial clone fetches missing blobs one at a time; sparse checkout needs the paths known in advance, which is exactly what an agent does not know before it searches. GFS keeps Git as the source of truth and changes only how a job consumes it: a pinned snapshot, lazy blobs, a copy-on-write overlay, remote revision-correct search, and hydration accounting that is enforced at the filesystem.

Imports bare Git repositories, resolves revisions, serves trees and blobs over HTTP/gRPC, answers search and history queries, resolves Git LFS pointers server-side out of its own LFS store, and runs a Git smart-HTTP gateway so stock git clone/fetch work against it. Lifecycle · one command, then ordinary tools

What happens when a workspace comes up

The steps below are a real sequence: each one depends on the previous, and the ordering is what makes the result safe to hand to an agent that will run whatever it likes inside it.

  1. 01

    Resolve the selector, pin the commit

    A branch name is only a selector. ResolveRevision or CreateMount returns a commit OID, and every later tree, blob, and search request names that OID. The mount does not move when the branch advances, so metadata from one generation can never be combined with file content from another.

  2. 02

    Take a retention lease before returning the handle

    Under the repository's ref lock the server writes a durable PREPARING lease, creates a reachability anchor at refs/gfs/mounts/{id}, marks the lease ACTIVE, and only then hands back the mount capability. A force push or a branch deletion upstream can no longer let git gc prune objects out from under a running job. The daemon heartbeats to renew; expiry is the crash fallback, with a grace interval before pruning.

  3. 03

    Mount over the workspace folder

    The daemon creates the folder with a real .git inside it, opens directory handles to that .git, then mounts the filesystem over the folder. The on-disk contents are now shadowed and reachable only through the daemon's retained handles. One folder holds everything; unmount leaves a plain working tree behind.

  4. 04

    Seed the Git surface so stock Git tells the truth

    The daemon writes a packed-refs carrying the repository's whole visible ref set — tags peeled, branches as refs/remotes/origin/* — plus an index stamped with the commit's deterministic snapshot time, a filter.lfs configuration, an fsmonitor hook, and objects/info/alternates pointing at the projected object store. git describe, git log origin/main and git status -sb's ahead/behind all answer without a fetch.

  5. 05

    The agent works with the tools it already knows

    Opening a file fetches one blob and caches it. Searching goes to the server index and fetches nothing. Writes copy up into the overlay. git status, git log, git diff, git commit and git rebase are stock Git over the projection — no forked Git, no synthesized index.

  6. 06

    Hand the work back

    gfs commit commits to the gateway's fork of the upstream, gfs push pushes upstream with the caller's own credential, and gfs export writes a bundle with a git apply-compatible patch and the base commit, so a downstream applier can reject or three-way merge stale work. Unmount never discards an overlay; cleanup is a separate, auditable action.

Architecture · three processes, one object database

Where the bytes live and who is allowed to move them

The Git object database is authoritative. Search indexes, decoded-blob caches, snapshot manifests, and every client cache are derived and can be rebuilt from it. FUSE privilege stays in a trusted host component; the agent container gets a bind-mounted workspace and a scoped socket, not a credential.

Mechanisms · the parts that carry the design

How it actually works

Each of these exists because a simpler version was measured and found wanting. The reasoning is recorded in twelve architecture decision records; what follows is the working version of each.

Lazy hydration client

lookup and getattr check the overlay, then the cached entry, then the server. open and read serve the overlay file or the immutable blob cache and fetch once on a miss. Cache entries are written to a temp file, hashed as a canonical Git blob, and atomically renamed, so a cache hit is cryptographically the same object as a server fetch.

The kernel cache is not enough on its own — FUSE does not cache directory listings and negative dentries expire quickly — so the daemon keeps complete base directory listings per pin. Against an immutable commit, one listing permanently answers a directory's children and the absence of every other name, which is what makes a warm git status cost zero round trips.

The cold walk is a different problem, and the daemon reads the access pattern to solve it: several listing misses descending from a common root are a tree walk, so it fetches that whole subtree with one ListTree and has the rest of the walk wait on it. Several distinct files read out of one directory are a directory being read through, so the rest of it is fetched in the background — bounded per file, per directory, and by what is left of the job's hydration budget.

Copy-on-write overlay client

The mounted base is immutable; every mutation is journaled. A whiteout represents a deleted base path, a rename is one atomic journal transaction, and the executable bit and symlink target are preserved. The first write to an existing file copies its blob up — unless O_TRUNC says the caller is replacing the whole file, in which case the old content is never downloaded.

Because the journal is the change set, status and diff are derived rather than scanned. On vscode, after five edits, gfs status answers in 10 ms without touching the tree; stock Git in the same workspace takes 0.30 s, and 2.3 s the very first time, because it insists on walking every directory once.

Raw Git over a projected object store ADR 0009

The earlier design synthesized a .git and shimmed a frozen grammar of Git subcommands. That grammar had to grow for every tool that exists — and an agent late in a session reverts to its strongest prior, which is git. So the gateway's real object database is projected into the mount instead, and stock Git answers for itself. 

core.checkStat     = minimal
core.trustctime    = false
core.untrackedCache = true
core.fsmonitor     = <journal-backed hook>
gc.auto            = 0
maintenance.auto   = false

None of that is enforceable — git -c core.checkStat=default status overrides it and costs 1 615 MiB — which is why the budget below is a prerequisite rather than a companion.

The hydration budget enforcement

Mandatory and default-on, because it is the only limit a renamed binary or a git -c override cannot bypass. Byte counting discriminates without a deny list: a configured git status touches zero tree bytes, while grep -r trips the limit inside 2 MB.

  • EDQUOT, chosen for its strerror: every tool prints "Disk quota exceeded" with the path. EIO would read as a corrupt filesystem.
  • Refuse at open and opendir, not at read, so a sweeping tool aborts instead of emitting one error per file.
  • Count unique blocks, so a re-read of an evicted block is free.
  • Separate counters for the working tree and the object store, so a legitimate blame cannot starve ordinary reads.

A mutually exclusive alternative — a cache residency budget that evicts and re-fetches instead of refusing — exists for hosts that would rather be slow than fail. It reports re-fetched over unique bytes, and its cache is scan-resistant.

64 KiB blocks, keyed by pack projection

Locating an object is a binary search and reconstructing one walks a delta chain, so object-store access is sparse and random — exactly what large chunks punish. The block size was measured, not chosen, and it matches FUSE's 128 KiB maximum read, so there is nothing to tune.

Blocks are keyed by (pack name, offset). A pack's filename is its own checksum, so those bytes are fixed forever and a cached block cannot go stale.

Revision-aware search server

Indexing every path and content pair per commit would multiply storage, so each unique searchable blob gets a stable numeric blob_key and is indexed once. A snapshot manifest supplies the sorted path → (mode, oid, blob_key) table, its reverse, and a Roaring bitmap of the keys reachable from that snapshot.

Literal search intersects trigram posting lists with the snapshot bitmap and then verifies candidate bytes for exact line, column, and snippet. Regex extracts required literals and verifies with regex-automata under scan and time budgets. Tantivy adds optional ranked token search over the same keys.

Silence is never ambiguous. Execution status (complete or truncated) and corpus coverage (binary, oversized, LFS, ignored — grouped by reason and scoped to the query's globs) are separate fields, and a successful search always ends with exactly one completion message. A missing terminal message is an error, never an empty result.

Server-side LFS expansion ADR 0012

An entry is an LFS entry when its path carries filter=lfs in .gitattributes at that revision and its blob parses as a v1 pointer. For those entries the metadata APIs report the expanded size and the content key lfs-sha256:{oid}, which the immutable blob endpoint serves from the LFS store. The mount, gfs cat, and WebDAV expand without knowing they did.

Shipping git-lfs in the image instead would have smudged gigabytes into the copy-on-write overlay, where the journal cannot tell a smudge from an edit — making an innocent gfs commit a corruption vector. Expansion is per entry: an object the store cannot fetch degrades that one file to its pointer, and nothing else.

The Git compatibility gateway server

A Rust gateway authenticates, authorizes, limits, and streams to a sandboxed stock git upload-pack child process — no shell, fixed argv and environment, read-only repository access. Protocol v2 ls-refs and fetch, shallow clone, and an explicitly configured partial-clone filter subset work; the refs/gfs/ lease namespace is hidden from advertisement and fetch.

Partial clone is controlled configuration, not merely a property of the Git binary: the gateway validates the exact requested filter before starting the subprocess, because Git's own per-filter settings can allow a family more broadly than GFS intends.

Time and inodes, specified client

Build systems depend on these, so they are not incidental. A raw committer timestamp is unusable — Git accepts future-dated commits — so the server records a sanitized snapshot_time once, clamped below its own first-seen time, and every base entry reports it. Overlay writes advance on a logical clock: 

new_time = max(host_wall_clock,
               snapshot_time + one_tick,
               prior_entry_time + one_tick)

So an acknowledged local mutation is always newer, even on a skewed host, and one index shipped with the commit is valid on every machine that mounts it.

Shims: a hint layer, not a boundary ADR 0007

gfs install-shim symlinks git, grep, find, and rg into a directory early on PATH. rg and find become their gfs equivalents with the same argv; recursive grep is translated conservatively; an unimplemented flag is refused by name at parse time, before any output exists, and the real tool runs over the mount instead — slow rather than wrong.

The git shim passes through by default. It routes blame and path-scoped history to the server, refuses gc, repack, prune, fsck, and maintenance with the reason, and delegates git clone to gfs clone. Outside a GFS workspace every shim is silent, which is what makes a PATH-wide install safe.

Commit correctness

The clone committed 105 changes; GFS committed 5

Both sides applied the same edit set — two modifications, one addition, one deletion, one rename — and committed with stock Git. Diffed against the base tree, the GFS commit contains exactly those five changes. The clone's contains 105: the five, one spuriously renormalized YAML file, and 100 deleted extensions/copilot/test/simulation/cache/*.sqlite paths.

Those hundred are Git LFS pointers. git-lfs is installed on this host, its smudge filter could not reach an LFS endpoint through the file:// mirror, and it left the files missing — which git add -A then recorded as deletions. The GFS workspace never ran a smudge filter: LFS is the server's job, and an object the store cannot fetch degrades to its pointer rather than to a hole.

Three steps that used to take minutes

None of them were the price of a working tree on the far side of a network. Each was a defect with one specific cause, and each is measured here before and after. The last card is not a defect: it is what reading objects you do not have actually costs.

Boundaries · stated, because they are invisible from inside

Where a GFS workspace is deliberately not a checkout

GFS is not a Git replacement — the server stores real Git repositories and speaks the real Git protocol. But a projected tree differs from git checkout in ways an agent cannot see unless they are written down.

ConcernRaw GitGFS
Getting started clone downloads history and checks out every file mount a pinned commit; blobs fetched on first open
Large monorepos partial clone fetches blobs one at a time; sparse checkout needs paths known in advance whole tree visible immediately; only touched files hydrate, with accounting
Code search git grep needs a local checkout server-side revision-aware search; zero client hydration
Edits the working tree is the checkout copy-on-write overlay over an immutable base
Large files git lfs pull smudges every object into each checkout server resolves LFS; the tree is born expanded, objects shared per host
Protocol — smart-HTTP gateway: stock clone and fetch work unchanged

No content filters except LFS

The mount serves raw blob bytes. .gitattributes text/eol conversion, core.autocrlf, and custom clean/smudge filters are not applied, so a repository that relies on them presents different bytes than git checkout would. LFS is the single exception, and it is resolved on the server rather than by the mount running a filter.

Repository formats are validated, not degraded

SHA-1 repositories with the files ref backend only. libgit2 cannot read reftable and its SHA-256 support is experimental, so the catalog rejects a mirror it cannot fully open rather than serving a partial view of it.

Platform and I/O shape

Linux and FUSE3 only, case-sensitive paths, whole-blob fetch, single-node server storage. Hard links return EPERM; xattrs and device nodes return a documented unsupported error; a gitlink appears as an empty read-only directory. The first open of a large LFS file blocks for a whole-object fetch and verify.

Honest about what FUSE cannot promise

Shims and search are cost measures, not security boundaries: a program that calls a binary by absolute path and opens every file will still hydrate every file — the budget, not the shim, is what stops it. FUSE sees file opens, not the intent behind them.

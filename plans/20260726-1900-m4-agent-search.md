# M4 — Revision-aware agent search

## Summary

M3 left a writable workspace: a pinned base served lazily over FUSE, a crash-safe
overlay on top, and `status`/`diff`/`export` derived from the journal without
scanning the base. What an agent still cannot do inside it is the operation it
performs more than any other — search the repository. Today the only option is
`rg` over the mount, which walks every directory and reads every file, hydrating
the entire monorepo and destroying the property the whole project exists for.

M4 replaces that with a server-side index over the pinned commit plus a local
search of the overlay, merged into one answer. PLAN.md section 7 sets four exit
criteria:

- supported literal/regex results match the documented `rg` semantics;
- search after edits returns the merged logical workspace;
- warm search meets the performance target and causes **zero** base hydration;
- **no tested failure or limit produces a result that is indistinguishable from
  "no matches"**.

The fourth is the one that shapes the design. An agent that receives an empty
result concludes the symbol does not exist; if a budget cut the query short, a
policy excluded the file, or the transport died before the terminal message, the
agent draws a false conclusion and acts on it. So every answer carries two
independent dimensions — **execution status** (did the query finish evaluating
the searchable corpus) and **coverage** (what was outside that corpus *within the
requested scope*) — and they map to distinct exit codes, frozen in ADR 0004:

| Outcome | Exit |
| --- | ---: |
| Complete, matches found | 0 |
| Complete, no matches | 1 |
| Missing terminal message / transport failure | 2 |
| Execution truncated (any budget, or no usable literal) | 3 |
| Coverage gap under `--require-exhaustive` | 4 |

Two M0 decisions are inputs and are not revisited. ADR 0004 priced the
representation on the worst-case repository — trigram postings at 0.15 bytes per
indexed byte, **1.99 MiB of manifest per snapshot**, 0.39 GiB for 200 retained
snapshots — and concluded that on-demand search of arbitrary commits is
affordable and need not be rationed. It also decided that **tokenized search
stays out of the MVP** (M4.4), on the measurement that a per-snapshot Tantivy
index costs 10.2 GiB where the trigram representation costs 150 MiB at the same
retention.

## Plan

Six phases, one commit each, each verified with `cargo build`, `cargo test`, and
`cargo clippy --all-targets -- -D warnings` before committing.

### Phase 1 — M4.1: blob registry and text classification

`gfs-search` stops being a placeholder. New dependencies: `roaring`, `memchr`,
`regex`, `rusqlite` (the same bundled SQLite the catalog uses).

- `classify.rs` — the corpus policy as data: binary (NUL in the first 8 KiB,
  ripgrep's rule), oversized (8 MiB), invalid UTF-8, generated, vendored. ADR
  0004 fixes the first two; the last three are *classifications*, not default
  exclusions, and PLAN.md is explicit that any exclusion must appear in coverage
  metadata. `CorpusPolicy` therefore carries which classifications exclude, so
  the declared policy and the enforced policy are the same object.
- `registry.rs` — repository-scoped blob keys assigned in one SQLite
  transaction, `intern` idempotent per OID, exclusion reason and size recorded
  per key.
- `lines.rs` — line boundaries over raw bytes, returning byte offsets into the
  blob. No normalization: a CRLF file's column must be the column in the file.
- `store.rs` — the SQLite schema, versioned and refused when newer, mirroring
  `catalog/schema.rs`.
- Budgets on ingestion: bytes-per-blob cap before any parse, and a bounded
  worker count, so a repository of generated minified files cannot monopolize
  the indexer.

### Phase 2 — M4.2: snapshot manifests

- `manifest.rs` — forward path table (sorted, front-coded), reverse table
  (blob key → path ordinals), Roaring membership bitmap, checksum, format
  version.
- `builder.rs` — full tree-walk construction over a `BlobSource` trait so
  `gfs-search` does not depend on `gfs-git`; parallel across a bounded worker
  pool. First-parent incremental construction that reuses the parent manifest
  and touches only changed paths.
- `prepare.rs` — READY/BUILDING/FAILED lifecycle, single-flight dedup of
  simultaneous preparation of the same commit, progress, retry, cancellation,
  TTL, and GC of manifests no longer pinned by a ref, lease, or TTL.
- `crates/gfs-service/src/search/` — an `IndexManager` per server holding one store per
  repository, wiring `PrepareSnapshot` to real manifest state and preparing
  configured branch tips eagerly.

### Phase 3 — M4.3: literal and regex index, and the completion contract

- `trigram.rs` — extraction, posting lists, compaction, lookup; literal-run
  extraction from a regex, conservative about optionality.
- `query.rs` — candidate intersection with the snapshot bitmap **before** any
  blob is read, exact verification against real bytes, path globs, case
  sensitivity, context lines, deterministic ordering, pagination.
- Bounded automata (`regex` size and DFA limits), and result/time/candidate/
  bytes/concurrency quotas.
- `proto/gfs/v1/search.proto` — `SearchService.Search` as a server stream whose
  messages are `oneof { match, completion }`, with exactly one terminal
  `completion`. The type makes "ended without a terminal message" representable
  so it can be tested rather than hoped for.

### Phase 4 — M4.4: token search

Skipped, per PLAN.md's own instruction and ADR 0004's measurement. Recorded
where a reader will look for it rather than left as an unexplained absence.

### Phase 5 — M4.5: overlay-aware client search

- `gfs-search::local` — search of overlay content, bounded the same way the
  server bounds itself: the same classification, a `.gitignore` matcher, and a
  time/bytes budget.
- The daemon's control socket gains `Search`. It queries the pinned commit
  (never the branch name), subtracts every path the overlay changed, deleted,
  renamed away from, or type-changed from the base results, adds local matches,
  and merges the two coverage reports into one scoped report.
- `gfs search` in `gfs-cli`: ripgrep-like text output, `--json`, coverage on
  stderr in text mode, and the ADR 0004 exit codes. `--require-exhaustive`
  promotes a coverage gap to a failure.
- `gfs rg` as a second binary: a safe flag subset that fails closed on anything
  unsupported rather than approximating it.
- `docs/agent-search.md` — agent instructions and the MCP tool schema, including
  the exit-code contract, because an agent that does not know about exit 3 is
  the failure mode the contract exists to prevent.

### Phase 6 — M4.6: correctness and performance

- `rg` over the M2 raw-tree materializer as the oracle, across a generated query
  corpus, on the fixture matrix.
- The awkward corpus: CRLF, no final newline, Unicode, invalid UTF-8 paths,
  repeated blobs, symlinks, binaries, huge lines, regex corners, overlay edits.
- Zero-hydration assertion: a server search over a clean workspace must fetch no
  blob bytes into the client cache.
- Cold/warm preparation benchmarks.
- Fault injection: budget exhaustion, each exclusion reason, index gaps,
  transport loss before the terminal message, partial backend failure — each
  asserted to remain distinguishable from an honest empty result.
- The M4 completion report and the PLAN.md status update.

## Decisions

**M4.4 is not implemented.** Recorded as an amendment to ADR 0004. The
implemented literal/regex engine covers the query shapes the pilot issues, and
the two properties a tokenizer would have been needed for turn out not to be
needed: substring matching inside identifiers is a trigram strength, and ranking
does not change which files an agent opens when it consumes `--json` and reads
all of it.

**A result's line text is capped, and the cap is a budget.** Also an ADR 0004
amendment, and the one decision M4 did not anticipate. A `Match` carries a copy
of its line, so retained memory is `matches × (1 + context lines) × line
length`; nothing bounded the last factor, and the fixture matrix's deliberate
4 MiB single-line file turned a `max_results: 10` query into a 45.5 GiB
out-of-memory kill. Three bounds now apply where the memory is spent rather than
where results are counted: a per-blob hit limit of `max_results + 1`, a per-line
`max_line_bytes` of 8 KiB, and a cumulative `max_display_bytes` of 64 MiB.
Exhausting the last is `TRUNCATED` with its own reason, because the contract's
rule is that an answer must never be quietly smaller than the question.

**Transport faults are injected with a stub service, not by breaking the real
server.** The property under test belongs to the client — a stream that ended
without a terminal message has to become `FailedBeforeCompletion` — and making
the real server produce that would mean giving it a bug. One test cuts a real TCP
connection alongside, so the stub is known to describe something the transport
does.

**Coverage is scoped to the request**, inherited from ADR 0004 and not
revisited. It was the rule that took the most discipline to keep: the temptation
at each step was to report everything the index knows about, and the reason not
to is that an agent seeing a warning on every query stops reading warnings.

## Details

Final numbers, test inventory, and the recorded gaps are in the
[M4 completion report](../docs/reports/m4-completion.md). Preparation and search
measurements are in
[`benchmarks/search-preparation.md`](../benchmarks/search-preparation.md),
reproducible with `cargo run --release -p gfs-server --example prepare-bench`.

Three gaps carry forward:

- the benchmark corpus is still the public stand-in set (open since M0.1);
- M4.5's own criterion — `gfs search` against `rg` over an overlay holding a
  full build tree — is a client-side measurement that has not been taken;
- index storage is 1.4× the M0 projection at the base, though the marginal
  per-snapshot cost the decision rested on matches at 1.9 MiB against 1.99.

# M5 — Git smart HTTP compatibility

## Summary

M1–M4 built the XVFS-native path: a pinned snapshot API, a lazy FUSE mount, a
crash-safe overlay, and revision-aware search. None of that speaks Git's wire
protocol. M5 adds the one thing that makes an XVFS-hosted repository usable by
tooling that is not XVFS — `git clone` and `git fetch` over smart HTTP — without
weakening any boundary the earlier milestones established.

PLAN.md section 8 sets two exit criteria:

- stock Git clone/fetch and partial-clone tests pass the declared
  version/feature matrix;
- Git traffic cannot bypass the same repository authorization used by XVFS APIs.

The accepted implementation (DESIGN.md 7.2, ADR 0001) is **not** a reimplemented
upload-pack. It is a Rust gateway that authenticates, authorizes, limits, and
streams to a sandboxed stock `git upload-pack` child. XVFS owns everything
outside the protocol; Git owns the protocol.

Three M0 findings are inputs and are not revisited:

- **ADR 0002**: protocol v2 serves any object in the object database by OID
  regardless of `uploadpack.allowAnySHA1InWant`. One bare repository is one
  authorization domain. The gateway enforces *repository* authorization and does
  not claim *object* authorization. PLAN.md M1.5 says plainly: do not write an
  acceptance test that expects the Git path to deny it.
- **M0.5 selected the synthesized `.git`**, so the promisor-remote bullet in
  M5.2 does not apply and the M2 → M5 dependency does not invert.
- **Three configuration traps** measured in M0.3 (`uploadpackfilter.blob:none`
  needs the colon, `GIT_EXEC_PATH` must survive `env_clear`,
  `uploadpack.packObjectsHook` must be unset rather than empty) each fail in a
  way that does not point at its cause. They are carried into the production
  code with the reasoning attached.

The probe in `spikes/gateway-probe/` proved the contract and buffers everything.
M5 owns streaming, backpressure, cancellation, reaping, limits, and auth.

## Plan

Four phases, one commit each, each verified with `cargo clippy --all-targets -D
warnings` and the relevant tests by name before committing.

### Phase 1 — M5.3: the subprocess contract

`crates/xvfs-server/src/gateway/`:

- `pkt.rs` — pkt-line framing, a bounded incremental parser, and the
  advertisement scanner that fails closed if a hidden ref reaches the wire.
- `upload_pack.rs` — the protected configuration, the allow-listed environment,
  `Git-Protocol` validation, filter policy, request validation, and the spawn
  itself. Everything the gateway may decide about the child is decided here and
  returned as data so a test can assert on it.

### Phase 2 — M5.1: the HTTP gateway

- `gateway/mod.rs` — the two routes on the existing HTTP listener, bearer and
  basic authentication, version-dependent framing, bounded gzip request bodies,
  streamed responses with backpressure, wall-clock and inactivity deadlines,
  concurrency admission, child reaping on disconnect, bounded and redacted
  stderr, and request telemetry.
- `Server::git_router()`, wired into `xvfsd-server` and `scripts/dev-stack.sh`.

### Phase 3 — M5.2: the protocol feature matrix

`crates/xvfs-server/tests/gateway.rs`: byte-exact v0/v1 and v2 advertisements,
clone/fetch across protocol versions, shallow, `blob:none`, rejected filters,
empty and packed and non-UTF-8 repositories, gzip bodies and a decompression
bomb, hidden-ref absence with a live lease anchor, authorization masking,
disconnect mid-pack, and a deterministic malformed-input sweep.

Every clone is verified independently — `git fsck` plus a tree comparison
against a direct filesystem clone — because the server's protocol engine *is*
stock Git and cannot be its own oracle.

### Phase 4 — documentation

`docs/reports/m5-completion.md`, the PLAN.md milestone row and section 8 status
block, and this file's Decisions and Details.

# M5 — Git smart HTTP compatibility

## Summary

M1–M4 built the GFS-native path: a pinned snapshot API, a lazy FUSE mount, a
crash-safe overlay, and revision-aware search. None of that speaks Git's wire
protocol. M5 adds the one thing that makes a GFS-hosted repository usable by
tooling that is not GFS — `git clone` and `git fetch` over smart HTTP — without
weakening any boundary the earlier milestones established.

PLAN.md section 8 sets two exit criteria:

- stock Git clone/fetch and partial-clone tests pass the declared
  version/feature matrix;
- Git traffic cannot bypass the same repository authorization used by GFS APIs.

The accepted implementation (DESIGN.md 7.2, ADR 0001) is **not** a reimplemented
upload-pack. It is a Rust gateway that authenticates, authorizes, limits, and
streams to a sandboxed stock `git upload-pack` child. GFS owns everything
outside the protocol; Git owns the protocol.

Three M0 findings are inputs and are not revisited:

- **ADR 0002**: protocol v2 serves any object in the object database by OID
  regardless of `uploadpack.allowAnySHA1InWant`. One bare repository is one
  authorization domain. The gateway enforces *repository* authorization and does
  not claim *object* authorization. PLAN.md M1.5 says plainly: do not write an
  acceptance test that expects the Git path to deny it.
- **M0.5 selected the synthesized `.git`**, so the promisor-remote bullet in
  M5.2 does not apply and the M2 → M5 dependency does not invert.
- **Three configuration traps** measured in M0.3 (`uploadpackfilter.blob:none`
  needs the colon, `GIT_EXEC_PATH` must survive `env_clear`,
  `uploadpack.packObjectsHook` must be unset rather than empty) each fail in a
  way that does not point at its cause. They are carried into the production
  code with the reasoning attached.

The probe in `spikes/gateway-probe/` proved the contract and buffers everything.
M5 owns streaming, backpressure, cancellation, reaping, limits, and auth.

## Plan

Four phases, one commit each, each verified with `cargo clippy --all-targets -D
warnings` and the relevant tests by name before committing.

### Phase 1 — M5.3: the subprocess contract

`crates/gfs-service/src/gateway/`:

- `pkt.rs` — pkt-line framing, a bounded incremental parser, and the
  advertisement scanner that fails closed if a hidden ref reaches the wire.
- `upload_pack.rs` — the protected configuration, the allow-listed environment,
  `Git-Protocol` validation, filter policy, request validation, and the spawn
  itself. Everything the gateway may decide about the child is decided here and
  returned as data so a test can assert on it.

### Phase 2 — M5.1: the HTTP gateway

- `gateway/mod.rs` — the two routes on the existing HTTP listener, bearer and
  basic authentication, version-dependent framing, bounded gzip request bodies,
  streamed responses with backpressure, wall-clock and inactivity deadlines,
  concurrency admission, child reaping on disconnect, bounded and redacted
  stderr, and request telemetry.
- `Server::git_router()`, wired into `gfs-server` and `scripts/dev-stack.sh`.

### Phase 3 — M5.2: the protocol feature matrix

`gfs-server/tests/gateway.rs`: byte-exact v0/v1 and v2 advertisements,
clone/fetch across protocol versions, shallow, `blob:none`, rejected filters,
empty and packed and non-UTF-8 repositories, gzip bodies and a decompression
bomb, hidden-ref absence with a live lease anchor, authorization masking,
disconnect mid-pack, and a deterministic malformed-input sweep.

Every clone is verified independently — `git fsck` plus a tree comparison
against a direct filesystem clone — because the server's protocol engine *is*
stock Git and cannot be its own oracle.

### Phase 4 — documentation

`docs/reports/m5-completion.md`, the PLAN.md milestone row and section 8 status
block, and this file's Decisions and Details.

## Decisions

**One HTTP listener, two merged routers.** The gateway lives on the existing
HTTP port rather than a third one: smart HTTP exists to work with the TLS,
proxies, and bearer credentials a deployment already has, and asking for another
port works against that. It is a separate `Router` merged into the HTTP one,
because the blob and webhook routes carry a 64 KiB body limit and a request
timeout that a `git clone` violates by design, and in axum a layer binds to the
routes of the router it was added to. Considered and rejected: one router with
per-route layers (fragile — the ordering of `.layer` calls decides which routes
are bounded) and a dedicated `--git-addr` (more configuration, no benefit).

**A bounded channel, not a buffered response.** The M0.3 probe buffered whole
responses; M5.1 owned streaming. Bytes cross a 16×64 KiB channel, so
backpressure is structural: a slow client fills it, the pump stops draining
stdout, the child blocks on its pipe. Measured consequence — the server peaks at
14 MiB RSS while a client pulls 6.4 GiB. Considered and rejected: `ReaderStream`
straight off the child's stdout, which gives no place to hang the inactivity
deadline, the output cap, the advertisement scanner, or the child's lifetime.

**The first chunk is awaited in the handler.** Once one byte of a `200` is on
the wire, a failure can only be signalled by truncating the stream. Awaiting the
first item costs nothing and means a child that dies immediately produces a
status code instead of an empty success.

**No `RLIMIT_AS`.** `upload-pack` mmaps packfiles; mapped pack bytes count
against the address-space limit, and the worst case in the M0.1 corpus has a
4.5 GiB pack. Any limit small enough to be a backstop breaks the repositories
GFS exists to serve. Memory is bounded by the cgroup — the same mechanism
ADR 0003's deployment model relies on. `RLIMIT_CPU` goes through `prlimit`,
because `pre_exec` is unavailable under `unsafe_code = "deny"`, and its absence
degrades to the wall-clock and inactivity deadlines rather than refusing to
serve Git.

**The reserved-namespace scanner runs on the advertisement only.** A pack
response carries arbitrary blob bytes, and a blob containing the ASCII
`refs/gfs/` is ordinary, so a scanner there would abort legitimate clones. The
advertisement is pkt-lines of ref names and never carries object content.

**Basic auth is accepted, not just Bearer.** Bearer is what a GFS-configured
client sends through `http.extraHeader`; Basic is what Git itself produces from
a credential helper or a URL userinfo. Refusing it would make every ordinary
`git clone` fail in a way the user cannot fix from the Git side. Twenty lines of
padded base64 rather than a dependency at the trust boundary —
`gfs_types::b64url_decode` is the url alphabet and unpadded, so it would reject
`+`, `/`, and `=`.

**No ADR.** Nothing here contradicts or extends an existing decision: ADR 0001
chose the sandboxed-subprocess architecture, ADR 0002 scoped the authorization
claim, and the filter policy is DESIGN.md 7.2's. The memory-limit omission and
the version-matrix gap are recorded in the completion report, where the rest of
the M5 evidence is.

## Details

Measured on `linux.git` (2 870 refs, 6.4 GiB), release server, stock Git 2.53.0,
protocol v2, loopback:

| | Wall time | Transferred | Server peak RSS |
| --- | ---: | ---: | ---: |
| v0 advertisement | 0.4 s | 244 KiB | 13 MiB |
| `--depth 1` | 14.5 s | 292 MiB | 14 MiB |
| `--no-checkout --filter=blob:none` | 161.4 s | 2.0 GiB | 14 MiB |
| full bare clone | 349.9 s | 6.4 GiB | 14 MiB |

Things worth knowing when touching this code again:

- **Every gateway test must be `multi_thread`.** They drive a blocking `git`
  client while the server runs in-process; on the default current-thread runtime
  the executor parks and the test hangs with no output and no failure.
- **`--filter=blob:none` without `--no-checkout` proves nothing**, and checking
  for a missing blob without `GIT_NO_LAZY_FETCH=1` fetches its own answer.
- **`remote.origin.partialclonefilter` is not evidence.** Git writes it from the
  command line whether or not the server honoured the filter.
- **Loose objects are mode 444.** A test that corrupts one must remove and
  recreate the file, not write over it.
- `uploadpack.packObjectsHook` is ignored by Git when it appears in
  repository-level config — Git documents this as a safety measure — and the
  suite asserts that rather than trusting it.
- The clone URL is `http://<http-addr>/v1/repos/<repository-id>`;
  `scripts/dev-stack.sh` clones and `fsck`s through it on every smoke run.
